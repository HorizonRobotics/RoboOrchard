1. Generate Config file

    Modify the script that generates the configuration file in `gen_sync_config.py` or `gen_async_config.py`

    The Piper command names match the dual-arm launch defaults:
    `left_joint1` through `left_joint6`, `left_gripper`, and the corresponding
    `right_` names. If you override the driver's `joint_names` list, update
    these command names, any observation selectors, and Pico's expected
    joint lists together. The default gripper label is `gripper`, not
    `joint7`; another label requires consistent explicit configuration.

    Joint observations now send the driver's `name` and `position` together
    as JSON under the existing channel key. Update the model server to parse
    this format before upgrading the client. Image/RTC binary arrays and
    response action arrays remain unchanged.

2. Launch deploy node

    ```bash
    # sync deployment
    bash launch_sync_infer.sh
    # async deployment
    bash launch_async_infer.sh
    ```

3. Control deployment in inference_app

    Now you could control deployment by inference_app:

    - Start inference.
    - Stop inference.
    - Reset the hardware scope configured for Control Manager.

    The App sends one global reset request. Control Manager gates commands,
    disables inference, resets the configured hardware, then remains in STOP.
    The default ALOHA configuration resets both master and puppet arms; the
    Pico configuration resets the two follower arms.

    Deploy may be left unstarted for teleoperation-only use. The default
    Manager configuration skips inference disable only when neither a
    configured Deploy node nor a disable service is currently discovered,
    without waiting for Deploy to appear. Once either is discovered, disabling
    inference must succeed before hardware reset, including when inference is
    already paused.
    See `../teleop/README.md` for optional-node and strict-reset settings.

    To change the reset scope, update `reset_services` in the configuration
    generated by `projects/HoloBrain/teleop/gen_control_manager_config.py`.
    AUTO selects model commands and TAKEOVER selects human commands; neither
    requires a different frontend workflow for ALOHA and Pico.

## Adapting the configuration

These generators are editable project examples, not a robot-discovery layer.
Start with the explicit left and right arm entries in `control_channels.py`.
The synchronous, asynchronous, and Control Manager generators share those
entries so Deploy's command topic stays aligned with Manager's input topic.

| Setting to change | Where to edit |
| --- | --- |
| Model response action keys | `server_output_key` in `control_channels.py` |
| Request keys for unpublished action steps (async only) | `server_remaining_key` in `control_channels.py` |
| Deploy output / Manager autonomous input topics | `autonomous_topic` in `control_channels.py` |
| Manager output topics connected to the drivers | `output_topic` in `control_channels.py` |
| ALOHA / Pico operator input topics | `override_topic()` in `control_channels.py` |
| Camera topics, image encoding, and model observation keys | `build_obs_channels()` in the selected `gen_*_config.py` |
| Joint order, velocity, and effort fields | `PIPER_JOINT_NAMES` in `control_channels.py` and `build_action_channels()` in the selected generator |
| Model URL, inference rate, control rate, and delay horizon | `main()` in the selected generator |
| Hardware enable/reset services and replay time | `../teleop/gen_control_manager_config.py` |

`name` is only the Manager channel label, for example `left_arm`. Renaming
it does not rename model fields or ROS topics. `side`, for example `left`,
is used by the example's joint-name and observation/teleop topic patterns.
If your robot does not use these patterns, replace the relevant expressions
with your actual joint lists and topics rather than encoding them in `name`.

`server_remaining_key` names a request field containing the channel's action
steps not yet published, not a remaining-action count. Change it to match
your model service independently of `server_output_key`.

Keep the sync and async examples aligned when supporting both modes. After
editing, regenerate the Deploy and Manager JSON configurations; changing a
Python generator does not update an already generated file or a running node.
